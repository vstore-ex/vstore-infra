# A15 capacity experiment — 2026-10-07

Historical report. See the [2026-10-09 follow-up](capacity-2026-10-09.md)
for the subsequent Redis AOF/current-backend runs and updated profile status.
The migration IP collision below was subsequently addressed by infra PR #62.

This draft delivers an isolated measurement harness and exploratory local
results. A15 remains open. No production limits, deployment workflows, VM size
or purchases were changed. The final 768 MiB worker profile is unverified:
its run was stopped at the owner's request to finish this PR.

## What was exercised

Docker Desktop Linux, ARM64, eight visible CPUs and 4,106,604,544 bytes of RAM.
Application images were rebuilt from the checked-out production source revisions:
backend `1e31490d3974548079d61532de1071f18c1b35f5`, frontend
`72f5450710c2cafcda9dfdccf5b4a0d969ce67d3`, admin
`82f004a7c2bd9e357d8a0e2662a673117da119aa`; infra base
`02f3f77faa9ad57e7573801c0552fb3a4210ed4e`.
They are local ARM64 builds, not the deployed amd64 image digests. The backend
build used an HTTPS Debian mirror in a disposable build directory after HTTP
package downloads failed integrity checks; application repository files were
not changed.

The fresh stack contained 100 synthetic games and 16 MiB of Redis fixture data.
Four closed-loop catalog readers and two media uploaders exercised actual API,
Pillow/WebP, Celery/FFmpeg and local Blob Storage operations. Fixtures were a
3840×2160 PNG (21,185,623 bytes) and a five-second 1080p/24fps H264 video
(8,083,248 bytes). Fixture hashes and image identities are in the evidence.

Phases: idle, mixed traffic, traffic overlapping PostgreSQL `pg_dump | gzip`,
an Alembic process and Redis BGSAVE, cooldown, then backend/worker recreation
after requests drained. Alembic was already at head: this measures its process
overhead, not a costly schema change. Recreation does not demonstrate zero
downtime. Certbot was an idle shell without ACME activity.

## Completed observations

Memory below is the largest simultaneous application stack working set,
`memory.current - inactive_file`. It includes migration overlap and excludes
the client, collector and local Blob emulator. MiB means 1,048,576 bytes.

| Phase | Baseline: concurrency 2 | Trial: concurrency 1, worker 512 MiB |
| --- | ---: | ---: |
| Idle | 453.7 MiB | 381.5 MiB |
| Mixed traffic | 1,138.0 MiB | 1,069.4 MiB |
| Snapshot/migration overlap | 1,565.9 MiB | 1,289.3 MiB |
| Cooldown | 1,407.7 MiB | 1,197.0 MiB |
| Recreation | 1,399.9 MiB | 1,194.5 MiB |

The baseline completed all five phases, HTTP checks, 44 video conversions,
Redis persistence and recreation with no OOM or unexpected restart. Its backend
kernel memory peak was 950.5 MiB against a 1,024 MiB ceiling: only 7.2% reserve.
Baseline runs report this margin; proposed profiles must have at least 15%.

The 512 MiB worker trial also completed the workloads with no OOM or unexpected
restart, but **failed the profile guard**: worker kernel peak was 488.3 MiB,
leaving only 4.6% reserve. Its backend peak was 821.7 MiB against 1,536 MiB.
This trial does not validate `config/capacity/candidate.json`, which now proposes
a 768 MiB worker and has not completed a validated run.

An earlier 30-second trial with backend 512 MiB, worker 384 MiB and admin 64 MiB
also completed requests without OOM, but touched backend/worker limits
(`memory.events.max` 4,170/926); admin reserve was only 2.7%. Replaying the current
guard rejects that trial. Successful requests alone do not establish headroom.

| Baseline workload | Mixed | Snapshot/migration overlap |
| --- | ---: | ---: |
| Catalog requests, all HTTP 200 | 1,093 | 1,044 |
| Catalog p95 | 56.6 ms | 82.1 ms |
| Image uploads, all HTTP 200 | 26 | 22 |
| Image upload p95 | 3.56 s | 4.77 s |
| Video uploads/completed conversions | 24/24 | 20/20 |
| Video upload p95, excluding async conversion | 179 ms | 254 ms |

During baseline overlap, minimum host available memory was 1,626.3 MiB,
host swap occupancy was zero and memory PSI some/full deltas were
20,604/19,259 microseconds. These describe the local test host, including other
Docker activity, not production. They are not latency or capacity guarantees.

## Evidence and limits

Sanitized evidence retains manifests, fixture identities, summaries, request
results, Redis persistence and container OOM/restart states:

- [Completed baseline](capacity/2026-10-07/baseline-pass.json)
- [Rejected 512 MiB worker trial](capacity/2026-10-07/candidate-verified.json)
- [Rejected smaller limits](capacity/2026-10-07/rejected-512-2.json)

Names identify local run directories; `candidate-verified` is a rejected trial,
not an approved profile. Raw samples remain local in `.capacity-results/`; their
SHA-256 hashes are retained. Run manifests record the exact harness source hashes
because the experiment code evolved during testing. Generated credentials,
database dumps, uploaded media and temporary Compose files are not committed.

Results are single short runs on a shared ARM host with synthetic data. The
Blob emulator itself reached its memory limit and could influence throughput.
Automatic CPU discovery in FFmpeg/Nginx differs from the two-CPU production host.
Half-second sampling can miss short simultaneous peaks; process RSS double-counts
shared pages and is diagnostic only. A final profile requires a completed run and
representative data on an isolated host with the reviewed amd64 images before
production adoption. This PR makes no VM selection or spending recommendation.

## Separate deployment finding

The first overlap attempt reproduced `Address already in use` when running a
second `backend` service while the existing backend held its fixed `proxy_net`
address. Production `deploy-service.yml` still uses
`release_compose run --rm --no-deps backend alembic upgrade head` (line 152);
the base backend service has that fixed proxy address.

The laboratory uses a separate migration service on `app_net`, which needs
database connectivity only. Production migration networking is unchanged here.
This is an actionable deployment handoff to fix separately before the next
backend release; the lab workaround is not a production fix.
