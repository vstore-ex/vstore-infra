# A15 x86-64 capacity qualification — 2026-10-14

Recommendation for owner review: **2 vCPU, 4 GiB RAM and Celery concurrency 1**
for the explicitly accepted starter workload below. The candidate completed
both three-minute workload phases, migration/persistence overlap and recreation
with at least 15% reserve in every application container. This is a memory
planning recommendation, not a measured Azure VM latency guarantee or permission
to resize production. The A15 measurement/recommendation deliverables are ready
for review; production adoption remains a separate owner decision.

## Scope and reproducible inputs

The owner accepted four concurrent catalog readers, two uploaders, 4K images
and 1080p videos as the starter envelope. Fixtures are 100 synthetic games, a
3840×2160 RGB PNG (20.2 MiB), a five-second 1080p/24 fps H.264 video (7.7 MiB),
and 16 MiB of Redis payload. Each mixed/deploy phase lasts 180 seconds; clients
are closed-loop with 200 ms reader delay. All accepted videos must finish.

Host: Arch Linux, Ryzen 7 PRO 4750U, 13.4 GiB RAM, Docker 29.8.1, Compose 5.5.1,
cgroup v2/systemd. Application/migration containers share CPU IDs `0,2`, two
physical cores; per-service CPU quotas remain enabled. Load generation/Azurite
are outside that CPU set and application memory sum. Existing host services
remained running; host RAM/PSI/swap therefore include unrelated activity.

Application and edge images were pulled as immutable linux/amd64 digests from
the latest successful deployment runs below, without rebuilding source or
copying production data/secrets. This identifies deployed CI artifacts; no
new production inspection or stress test was performed.

## RAM recommendation and cost tradeoff

| Budget item | MiB | Basis |
| --- | ---: | --- |
| Application + migration peak | 1449.6 | Measured simultaneous memory.current |
| OS / Docker | 768 | Planning allowance for a minimal dedicated Linux VM |
| Maintenance / backup tooling | 256 | Planning allowance, not a restic measurement |
| PostgreSQL/data growth | 512 | Planning allowance beyond the starter fixtures |
| Total planned use | 2985.6 | Measured demand + explicit allowances |
| Remaining on 4 GiB | 1110.4 (27.1%) | Additional reserve |

A 1 GiB host is below measured application demand before OS/maintenance.
Choose 4 GiB as the reviewed starting budget; 2 GiB does not preserve these
allowances. Do not derive VM RAM by adding container ceilings. The 4 GiB
aggregate was not imposed on the ThinkPad; this budget is an inference from
measured demand and stated allowances, not a completed 4 GiB VM test.

## Coverage, limitations and verification

The owner-approved starter envelope qualifies these images for this bounded
capacity recommendation. Larger catalogs/media, sustained loads, expensive
future data migrations and cloud-specific performance require new qualification.
Alembic was already at head. The overlap deliberately keeps the API live while
snapshot/migration run; production stops the API first. Recreation follows
request drain. This measures memory overhead, not zero-downtime release or
backup restoration. No production application, schema, limits or access changed.

The earlier x86-baseline-1 attempt failed before load because root without
DAC override could not write a private host result directory. Probe/collector
now use the invoking host UID/GID; a regression test covers this Linux behavior.
The failed preparation run is excluded from successful measurement evidence.

127 unit tests passed. Native x86 baseline/candidate CLI runs passed coverage;
candidate reserve passed. Frontend/admin Nginx checks with
`--add-host backend:127.0.0.1` passed. Compose config and diff checks passed.
Application API tests traverse the actual edge/storefront/admin images.
