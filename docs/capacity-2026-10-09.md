# A15 capacity follow-up — 2026-10-09

The 768 MiB worker candidate completed a validated local run. Every application
container retained at least 15% kernel-peak reserve, with no limit enforcement,
OOM or unexpected restart. This validates the bounded local scenario; A15 stays
open for representative amd64 qualification before any production adoption.

## Inputs and changes

The branch incorporates infrastructure main `069cc8b`, including Redis AOF
policy (A07), off-host backup tooling (A06) and migration recovery (PR #62).
The lab does not run the backup scheduler or the production release workflow.

Both final runs used the same harness, application images, test host and workload.
Backend source is `079a12f8c40cb7c3e5a4d43a1eb5b067697d0e3d` (UUID game IDs).
The local backend image overlays that tracked source on the previous local runtime;
`requirements.txt` is byte-identical, so runtime dependencies were reused without
network installation. Frontend/admin/edge images are the local builds identified
in the manifests. All application images are ARM64 local builds, not deployed
amd64 digests. Docker Desktop exposes eight CPUs and 4,106,604,544 bytes of RAM.

The probe now records and uses created game IDs and reuses startup-seeded admin
records. A regression test checks actual catalog/upload request URLs with UUID
fixtures. The collector handles both capitalized and lowercase Docker
`no such object` messages during recreation. An earlier current-backend attempt
completed its HTTP/video work but failed on that inspection race; it is not
included as a passing run.

Azurite's test-only ceiling is now 1,024 MiB, after preliminary 256/512 MiB runs
observed limit pressure. It remains excluded from the application stack budget;
its memory/events are reported separately. Redis retains AOF everysec,
noeviction and the base 64 MiB data budget. Reports verify successful AOF writes,
AOF rewrite status and explicit RDB snapshots. Old 2026-10-07 results have different
backend, Redis and emulator settings; they are historical trials, not controls
for this comparison.

## Recommendation and remaining scope

Use the checked-in concurrency-one profile as the starting point for a reviewed
amd64 replay. Its ceilings are test inputs, not a production configuration change
or a VM sizing formula. Do not infer RAM demand by adding those ceilings. No cloud
alternatives, purchases, resize or production stress are part of this PR.

The overlap phase deliberately keeps the API live next to a migration process;
production PR #62 now stops the API before migration. Alembic is already at head
and the small snapshot covers only synthetic fixtures. Recreation runs after
requests drain. This does not certify expensive migrations, backup scheduling,
release failure recovery, zero downtime, production data sizes or sustained load.
A15 remains open; this PR can be reviewed independently as experiment tooling.
